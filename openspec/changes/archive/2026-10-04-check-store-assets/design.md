## Context

See `proposal.md` — Why for the incident. What shapes the approach:

- Play's phone-screenshot rules are short and specific: 320–3840 px on each
  side, an aspect ratio of 16:9 or 9:16, at least 2 and at most 8 per language.
  The icon must be 512×512 and the feature graphic 1024×500. These numbers are
  currently written only in the header comment of
  `scripts/make-store-screenshots.ps1` and in `listing.md`; nothing enforces them.
- The committed gallery is `app/android/store-listing/screenshots/NN-<slug>.png`,
  where the numeric prefix *is* the gallery order (the hero first). The uploads
  append in file order, so the filename order is the published order — which is
  why the ordering rule is a correctness property, not cosmetics.
- The converter needs ImageMagick 7 and a font (Montserrat) to regenerate the
  assets. CI runners have neither by default. The check therefore must not
  regenerate anything: it only reads what is committed.
- PNG dimensions are in the IHDR chunk of the first bytes, so a standard-library
  reader gets width, height and the colour type with no image dependency. A
  content hash for the duplicate rule comes from `hashlib`.
- CI is `windows-latest`, and the repository already runs Python in
  `pages.yml`, so Python needs no new runner setup. The release workflow already
  asserts that vendored libraries reached the packaged artifact; this check is
  the same kind of assertion, on a different artifact.

## Goals / Non-Goals

**Goals:**

- A wrong-sized, over-count, duplicated or ambiguously ordered asset set fails
  before publication, with a message naming the file and the rule.
- The check runs without ImageMagick, so it is cheap enough to run on any change
  to the assets.
- Every violation is reported in one pass, because fixing assets one error per
  run is the loop this change exists to end.

**Non-Goals:**

- Regenerating, re-encoding or re-ordering assets.
- Uploading to Play, or deciding what the gallery should contain.
- Validating the listing *text*; those limits belong with the copy.

## Decisions

**D1 — Read the PNG header directly; add no image dependency.**

Parsing IHDR is a few lines and removes ImageMagick, Pillow and font
configuration from the check's requirements. That is what makes the check cheap
enough to trigger on asset changes, and it means the check and the converter
cannot disagree about how to read a file.

*Alternative considered:* shell out to `magick identify`. Rejected: it couples
the check to a tool the CI image does not have, so the check would be skipped
exactly where it is most needed.

**D2 — Read the limits from one place, and print them in the failure messages.**

The bounds, ratios and counts live as named constants in the check, and each
failure names the limit it broke. `listing.md` then states the same table in
prose, with a pointer to the script as the enforcing copy. Two hand-maintained
copies of a rule table will drift; a prose table that points at the enforcing
script cannot drift silently.

*Alternative considered:* keep the numbers only in `listing.md` and have the
script parse the markdown. Rejected: parsing prose to enforce a rule makes the
check's correctness depend on documentation formatting.

**D3 — Uniqueness by content, not by name.**

The incident was not a name clash; it was a file whose *name* changed while its
bytes did not, leaving an identical file under the old name. Comparing content
hashes catches exactly that, and also catches the same screenshot captured twice
under two names — the other way a gallery picks up a redundant entry.

*Alternative considered:* only checking that prefixes are unique. Insufficient on
its own, and it is the weaker of the two rules here.

**D4 — Ordering means unique and contiguous prefixes from 1.**

Requiring contiguity means a missing slot (`1,2,4,5`) is an error rather than a
silent skip, which is the failure mode when a capture is dropped and the rest are
renumbered by hand. It also makes the published order fully determined by the
filenames, so the Console and the repository cannot disagree about which shot is
the hero.

**D5 — Check the listing icon and feature graphic too, by presence and size
only.**

They are generated by `make-app-icons.ps1`, so content correctness is not in
question; what can go wrong is that a regeneration silently changed a dimension
Play then rejects. A presence-and-size assertion is the proportionate check.

**D6 — Run it in two places.** A step in the release workflow, beside the
existing packaged-artifact assertion, so a release cannot ship a bad set; and a
path trigger on the assets and the converter, so a mistake is caught at the
commit that introduces it rather than at the next release. A standalone trigger
on the check script itself keeps it from rotting untested.

## Risks / Trade-offs

- **A false failure blocks a release.** → Every rule is a published Play limit,
  not a house style, and the messages name the limit. The check is deterministic
  and reads only committed bytes, so it cannot flap.
- **The duplicate rule could reject a legitimate gallery.** → Only byte-identical
  files are rejected. Two genuinely different screenshots of the same screen at
  different moments differ in bytes and pass.
- **Contiguity could annoy someone who wants gaps in the numbering.** → Gaps
  carry no meaning here, and a gap usually means a shot was dropped.
- **The check cannot catch a *wrong* screenshot** — an image that is
  well-formed but shows the wrong thing. That is a human judgement; the check
  exists to stop the mechanical failures, and `listing.md` remains the place a
  maintainer states what each shot is for.
